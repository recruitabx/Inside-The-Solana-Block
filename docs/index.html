Method

One request, two transactions, one block

01

A conflicting pair

Two of our own transactions, from two payers, both writing one fresh shared account. The scheduler must put one before the other. The compute unit price differs 5,500x: 5,500,000 vs 1,000 micro-lamports per CU.

02

Randomized fee and request position

Which transaction is high-fee and which goes first in the request are drawn independently. Sent as one JSON-RPC request about 270 ms before the target's leader window; a separate arm sends two requests 200 ms apart.

03

Block producer read from the block

A pair is usable only if both transactions sit in one block produced by the target, read from the block's Fee reward and never assumed from the schedule, inside the targeted window.

04

Preregistered and anchored on mainnet

Estimands, thresholds, N of at least 100 and the equivalence margin were fixed before the data. Hashes of the plan and of the data were written to mainnet as memo transactions.

The six considerations

How the design handles each point of the bounty, shortened from docs/DESIGN.md.

01Leader schedule and leader types

Windows are 4 slots and 4-aligned (measured). Targets are frozen identities, one per client type, chosen by a stated rule that requires a stable gossip claim (same clientId and version over at least 18 hours) because claims flap: 33 of about 3,900 nodes changed claim within 80 minutes on 2026-10-30.

02Path from our backend to the executing node

Our VM cannot send UDP or QUIC, so every transaction goes as an HTTPS JSON-RPC request to one provider.

03Interaction of our own transactions with each other

Within a pair the interaction is the design (shared W in arms P, E, S; none in arm D). Across pairs there is none by construction: one probe per window, a fresh W per probe, distinct payers, a payer reused only after confirmation or expiry, at least 2 s between probes.

04Competition inside the block

Other transactions compete with ours. Ours sit high in the priority queue (about 1.1 and 3.4 lamports per cost unit, while 18% to 50% of transactions pay no priority fee), so the leader can schedule both promptly; the order between them is still the leader's decision.

05Send order

The position of the high-fee transaction in the request is randomized independently of the fee assignment, giving q as a second estimand. The spaced arm sends two requests 200 ms apart in random order, the only arm with a known send order, to test for an arrival rule and for overtaking.

06Noise versus rule

Pre-specified estimands and verdict thresholds; an equal-fee arm as the noise floor; an equivalence test (90% intervals of both p and q inside [0.35, 0.65]) as the only route to "no rule detected"; Holm correction over all tests; synthetic data with planted rules and two localnet known answers as checks on the analysis code.

Honest limits

What we do not separate

  • 01Arrival order at the leader is not observable (no direct QUIC from our machine); q measures request position, and arm S shows that spaced arrival order wins.
  • 02Fee-dependent routing by the provider is not separated from a fee rule at the leader.
  • 03External builders (BAM node, Harmonic builder) are not separated from the validator's own scheduler.
  • 04Operator configuration is not separated from client software: each verdict describes one validator.
  • 05Co-presence in the scheduler buffer is not observed directly; p is a lower bound on a priority rule's strictness.
  • 06Client identity is a self-reported gossip claim; it was snapshotted at every run start and end (33 of about 3,900 nodes changed claim within 80 minutes on 2026-10-30).

The full list of problems, in order, is in What went wrong in the report.
